# Reproducible performance and operational policy

Prepare the pinned packages, then run `node scripts/run-reference-graph-benchmark.mjs smoke`, `load`, or `soak`.
Each run copies and verifies an immutable testkit snapshot before spawning an isolated 1 GiB process and separate
loopback 2 GiB Fuseki with newly created TDB2 files. The snapshot configuration, package hash, execution state and final
report hash remain in `java/graph-testkit/target/reference-*/`. The runner does not forward live credentials.
Review evidence can preserve these generated bytes under `docs/graph-migration/evidence/raw/`; that directory and
`docs/graph-migration/release/` are excluded from formatting so producer checksums remain verifiable.

`smoke` exercises actual TDB2, structural/SHACL validation, typed golden reads, mixed CRUD, idempotent replay and real
after-commit worker death/resume. It is **not** the streaming-load or two-hour gate. `load` requests 100,000 vertices and
1,000,000 edges with one warm-up and three measured repetitions. `soak` requests at least 7,200,000 ms of mixed workload.
The reports distinguish profile/duration acceptance, unresolved batches, heap after GC and queue/scaling thresholds.
Incomplete or resource-blocked runs are not acceptance evidence. Never overwrite an executing snapshot.

Reproducible packaging fixes archive timestamps and forces the pinned Maven JAR plugin to recreate unshaded inputs
before each Shade invocation. Incremental builds must not re-shade their own previous output. This follows the
[Maven JAR 3.4.2 `forceCreation` contract](https://maven.apache.org/plugins-archives/maven-jar-plugin-3.4.2/jar-mojo.html).
Compare all three packaged SHA-256 values across consecutive builds. Dependency SBOM/license goals run in `verify`,
not merely `package`; a successful package banner is not dependency-report evidence.

Worker configuration caps queued/batched records at 1,000, batch payloads at 8 MiB and individual canonical records
at 1 MiB. Target response bodies have a separate 32 MiB ceiling enforced during receipt, including streaming reads.
The configured request deadline covers receipt of the complete body, not only response headers. Oversized responses
are explicit nontransient failures; reconcile uncertain writes before changing queries or retrying.
Structural validation hashes the bytes actually consumed and checks the selected source before and after validation.
Partition/label inventory is bounded to 10,000 distinct entries and 4 MiB of UTF-8 keys; exceeding either bound blocks
the report rather than dropping inventory or claiming a sampled validation passed.

Migration metrics distinguish source records/second, data quads/second and request-body bytes/second. The bounded
1-percent logarithmic latency estimator measures batch confirmation/checkpoint latency; it is not per-request latency.
Worker heap/GC and queue/retry observations are reported. Body bytes exclude HTTP/TLS overhead. Worker RSS, target
CPU/RSS/disk utilization/latency and actual network bytes are explicitly unobserved in this portable harness; collect
platform counters alongside the owned processes when establishing a reference host. No universal throughput is promised.

`node scripts/benchmark-graph-paths.mjs --private-fixture-confirmed` separately measures actual Jena
mapping/serialization and paired-graph pre-serialized RDF loading, followed by the native typed query/CRUD fixture
runner. It uses a bounded semantic fixture with one warm-up and three measured repetitions on a newly created private
TDB2 target. Update-request p50/p95/p99 is observed in this path; mapping and application timings include Java CLI
startup and documented validation overhead. It is not the 100,000/1,000,000 streaming-load gate.

The reference harness executes canonical loading/recovery, golden translated reads, CRUD and mixed workload paths.
Live extraction-only and extraction-to-load measurements require opted-in source configuration and scoped RU budgets;
they are blocked without it. Isolated stage and request timings remain distinct from migration measurement and must
not be inferred from aggregate load throughput.

Evaluate a measured report with:

```
node scripts/evaluate-graph-performance.mjs report.json policy.json new-evaluation.json [baseline-report.json]
```

Policy follows `schemas/graph-migration/performance-policy.schema.json`. Supply minimum source records/second,
maximum p95 batch milliseconds, maximum request error rate and maximum RU charge as applicable. A null threshold is
unestablished, not passed. Missing request-failure denominators and local-only RU observations remain unestablished
even when a threshold is supplied. `benchmarks/unestablished-policy.json` does not invent operational SLOs.

Thresholds apply to the worst measured repetition. Baseline comparison uses medians and requires identical dataset
hash, configuration hash and reported environment. Throughput degradation **over** 15% or p95 degradation **over**
20% is flagged for repetition/investigation; a single flag is not an automatic performance rejection.
Host co-tenancy, CPU/storage pressure and instrumentation must be controlled when establishing a stable baseline.

CI runs offline acceptance on Linux and Windows. Reference load/soak is explicit workflow-dispatch opt-in, not a short
PR smoke substitution. The protected live job is read-only, fails blocked without configuration, and does not upload
sensitive source evidence. Source population, write capability probes and cleanup are not authorized by that job.
